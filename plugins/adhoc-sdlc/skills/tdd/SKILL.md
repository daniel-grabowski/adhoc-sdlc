# TDD

## What

`tdd` is a discipline for writing code in small cycles that start with a failing test. It applies to new features, bug fixes, refactoring, and behavior changes. It uses the project's own test framework and commands; it adds no tooling.

## Why

A test written after the code passes at once, so it proves nothing about whether it can catch a defect, and it tends to describe the implementation instead of the intended behavior. A test you watched fail for the right reason proves it checks something real. The cycle also keeps each step small enough to reason about.

## The rule

```text
No production code without a failing test first.
```

If code was written before its test, discard that code and implement it again from the test. Keeping it "as a reference" or adapting it is writing the test after.

## When to use

Always for features, bug fixes, refactoring, and behavior changes. Exceptions need the user's agreement: throwaway prototypes, generated code, configuration files. "Skip it just this once" is the signal to stop and follow the cycle.

## Cycle

### Red: one failing test

Write one test for one behavior.

- The name describes the behavior ("rejects an empty email"), and "and" in the name means two tests.
- It exercises real code. Use a mock only when the dependency cannot run in a test (network, clock, external system), and never assert on the mock's own behavior.
- Before writing it, name the production change that would make it fail. If you cannot, the test checks nothing.

### Verify red: watch it fail

Run it. Mandatory.

- It must fail, not error out. A compile error, a typo, or a missing import is not a red test: fix it and run again.
- The failure message must be the one you expect, and the cause must be the missing behavior.
- If it passes at once, it tests behavior that already exists. Fix the test.

### Green: minimal code

Write the simplest code that makes this test pass. Add no options, no generality, and no behavior the test does not ask for.

### Verify green: watch it pass

Run it. Mandatory.

- The new test passes.
- The project's whole test suite passes, not only the new file. A scope statement for the task bounds the deliverable, not the verification. Any failure the run shows, including one you did not cause, goes into the report by name.
- The output has no new errors or warnings.
- If the test fails, fix the code, not the test.

### Refactor: only on green

Remove duplication, improve names, extract helpers. Do not add behavior. Keep the suite green after each step.

### Repeat

The next failing test starts the next cycle.

## Bug fixes

A reported bug first becomes a failing test that reproduces it. The fix makes it pass, and the test stays as the regression guard. Use the `debug` skill (invoke it as `$<name>`) to find the cause before writing that test when the cause is not yet known. Do not fix a bug without a test.

## Rationalizations

| Excuse | Answer |
|--------|--------|
| "Too simple to test" | Simple code breaks too, and the test takes a minute. |
| "I will add tests after" | A test that passes at once proves nothing; you never saw it fail. |
| "I tested it by hand" | Manual checks leave no record and cannot be re-run on the next change. |
| "Deleting the code is wasteful" | The time is spent either way; code you cannot trust is the waste. |
| "I need to explore first" | Explore, throw the exploration away, then start with the test. |
| "The test is hard to write" | Hard to test means hard to use; simplify the design. |
| "TDD is dogmatic here" | The cycle is the cheaper path; shortcuts return as debugging. |

## Red flags

Stop and restart the cycle when any of these appears:

- code before the test, or a test added "later";
- a test that passes on the first run;
- a failure you cannot explain;
- a mock-heavy test that asserts on the mock;
- "this case is different".

## When stuck

| Problem | Move |
|---------|------|
| You do not know how to test it | Write the API you wish existed, then the assertion first. |
| The test is too complicated | The design is too complicated; simplify the interface. |
| Everything must be mocked | The code is too coupled; pass dependencies in. |
| The setup is huge | Extract helpers; if it is still huge, simplify the design. |

## Done checklist

- Every new function or behavior has a test.
- Each test was seen failing for the expected reason before the code existed.
- Each test was satisfied by minimal code.
- The whole suite passes and the output is clean.
- Edge cases and error paths are covered.

If a box cannot be checked, the cycle was skipped: say so in the report instead of claiming green.

## Optional steps

Both steps are optional; use them where they help, not by reflex.

- `cove`: when a test assumes a fact you cannot see directly (the exact error an external library raises, a documented default, a protocol detail), run the `cove` skill (invoke it as `$<name>`) on that claim before encoding it in a test. Skip it for behavior you define yourself.
- `temper`: when the change is risky or wide and the test strategy itself is in doubt (what to cover, what to fake, where the seams are), run the `temper` skill (invoke it as `$<name>`) on that strategy before writing the first test. Skip it for a small change.

Neither skill replaces the cycle above, and this skill does not repeat their procedures.

## Output

Return to the caller:

- the tests added or changed, each with the failure seen before the code and the pass after;
- the result of the whole suite, including failures you did not cause;
- what stays untested and why.

Keep it short: omit anything empty.
